# cookie-prefs design

Contract for the implementation. The public types in `src/index.ts`, `src/core/types.ts`,
`src/react/index.tsx`, `src/script/index.ts`, `src/next/index.tsx`, `src/theme/index.tsx`,
`src/theme/server/index.ts`, `src/theme/next/index.ts` and `src/theme/color/index.tsx` are final; `src/core/__tests__/types.test-d.ts` pins their inference and is checked by
`npm run typecheck`. Change the API only together with this document.

> nuqs keeps state in the URL; cookie-prefs keeps it in cookies, so the server knows it before the first render.

## Usage

### `cookie-prefs` (core, no DOM required, zero dependencies)

```ts
// app/prefs.ts: a plain module, imported by server and client code
import { definePrefs, pref } from 'cookie-prefs'
import * as z from 'zod' // any Standard Schema validator, optional

export const prefs = definePrefs({
  theme: pref.enum(['light', 'dark', 'system']).default('system').reflect('class'),
  sidebar: pref.boolean().default(true).reflect('data-sidebar'),
  density: pref.enum(['compact', 'cozy']).default('cozy').reflect('data-density'),
  pageSize: pref.number().default(25),
  locale: pref.string(), // string | undefined
  columns: pref.json(z.array(z.string())).default([]),
})

prefs.sidebar.get()                     // boolean, from document.cookie
prefs.sidebar.set((open) => !open)      // writes the cookie, syncs other tabs
prefs.theme.reset()                     // deletes the cookie -> 'system'
prefs.theme.subscribe((theme) => {})    // returns unsubscribe

// any server: Request handler, middleware, Remix loader, Astro
readPrefs(prefs, request.headers.get('cookie')) // { theme, sidebar, ... } typed
prefs.locale.read(request.cookies)              // one pref
response.cookies.set(prefs.locale.toCookie('de'))
```

### `cookie-prefs/react`

```tsx
'use client'
import { usePref } from 'cookie-prefs/react'

const [sidebar, setSidebar] = usePref(prefs.sidebar)
<button onClick={() => setSidebar((open) => !open)}>Toggle</button>

// non-Next SSR (Vite, Remix, TanStack Start): wrap the app once
<PrefsProvider snapshot={snapshotPrefs(prefs, cookieHeader)} script={prefsScript(prefs)}>
  <App />
</PrefsProvider>
```

### `cookie-prefs/script`

```ts
import { prefsScript } from 'cookie-prefs/script'

prefsScript(prefs) // source of the pre-paint script, '' when no pref reflects
```

Its own entry, so the inline script source is not part of the core bundle. It has no runtime imports: it reads the reflection config from the handles (see Duplicate copies), so it works with handles from any copy of the core.

### `cookie-prefs/next` (App Router, server-only entry)

```tsx
// app/layout.tsx
import { PrefsProvider } from 'cookie-prefs/next'
import { prefs } from './prefs'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" suppressHydrationWarning>
      <body>
        {/* mode="script" (default): route stays static; mode="server": exact SSR from request cookies */}
        <PrefsProvider prefs={prefs}>{children}</PrefsProvider>
      </body>
    </html>
  )
}

// any Server Component (makes that route dynamic)
const { sidebar } = await getPrefs(prefs)
```

### `cookie-prefs/theme` (next-themes compatible)

```tsx
- import { ThemeProvider, useTheme } from 'next-themes'
+ import { ThemeProvider, useTheme } from 'cookie-prefs/theme'

<ThemeProvider attribute="class" defaultTheme="system" enableSystem>{children}</ThemeProvider>

const { theme, resolvedTheme, setTheme } = useTheme()
```

### `cookie-prefs/theme/server` and `cookie-prefs/theme/next` (opt-in, server-only)

```tsx
// any server: React Router / Remix loader, Request handler
import { readTheme } from 'cookie-prefs/theme/server'
readTheme(request.headers.get('cookie'), { themes: ['light', 'dark'] }) // 'light' | 'dark' | 'system'

// Next.js App Router (makes the route dynamic)
import { getTheme } from 'cookie-prefs/theme/next'
const theme = await getTheme({ themes: ['light', 'dark'] })
<html lang="en" className={theme == 'system' ? undefined : theme} suppressHydrationWarning>
```

| Entry | Export | Imports at runtime | Budget (gzip) |
| --- | --- | --- | --- |
| `cookie-prefs/theme/server` | `readTheme(source: CookieSource, options?: ThemeOptions<T>): T \| 'system'` | `cookie-prefs` | 255 B |
| `cookie-prefs/theme/next` | `getTheme(options?: ThemeOptions<T>): Promise<T \| 'system'>` | `cookie-prefs`, `cookie-prefs/next`, `cookie-prefs/theme/server` | 200 B |

### `cookie-prefs/theme/color` (opt-in, client)

```tsx
import { ThemeColor } from 'cookie-prefs/theme/color'

<ThemeProvider attribute="class">
  <ThemeColor colors={{ light: '#ffffff', dark: '#0a0a0a' }} nonce={nonce} />
  {children}
</ThemeProvider>
```

| Entry | Export | Imports at runtime | Budget (gzip) |
| --- | --- | --- | --- |
| `cookie-prefs/theme/color` | `ThemeColor(props: ThemeColorProps): ReactElement`, `ThemeColorProps { colors: Readonly<Record<string, string>>; nonce? }` | `cookie-prefs/theme`, `react` | 1030 B |

## Decisions

1. **One cookie per pref**, named `prefix + key` (`prefix` defaults to `''`; per-pref `.options({ name })` overrides). Independent writes from two tabs cannot clobber each other (no read-modify-write of a shared blob), each pref gets its own attributes, the 4 KB cookie limit applies per pref, and cookies stay readable in devtools, middleware and the inline script. Cost: a few bytes of header per extra pref.
2. **Cookie defaults**: `Path=/`, `SameSite=Lax`, `Max-Age` 400 days (the RFC 6265bis cap; every write refreshes it), no `Domain`, `Secure` added automatically on `https:` pages for browser writes and omitted by `toCookie()` unless set. Override for all prefs in `definePrefs(shape, options)` or per pref with `.options()`; an option set to `undefined` (`prefix` and `name` included; also `null`, which only JavaScript callers can pass) is ignored, so the value falls through to an earlier `.options()` call, then the `definePrefs()` options, then the default. Prefs are never `HttpOnly` because the browser writes them, so they are readable by any script: never store secrets or session data in a pref.
3. **Builder, then handle**. `pref.*` returns an immutable builder carrying a type-only `'~types'` marker (`PrefTypes<T, V>`); `definePrefs` turns each into a `Pref<T, V>` handle (codec + cookie name + store). `T` is the writable type, `V` is `T` with a default or `T | undefined` without. The handle is what `usePref` takes and works outside React. The setter takes `T | ((prev: V) => T)`; clearing is `reset()`, never `set(undefined)`.
4. **Server snapshot**: the provider carries `PrefsSnapshot`, the raw cookie strings of only these prefs (serializable across the RSC boundary, never other request cookies). `usePref` uses `useSyncExternalStore` with `getServerSnapshot = parse(snapshot[name])`, or the default when there is no snapshot (script mode), so SSR and hydration render the same value; afterwards it reads `document.cookie`. Values only the client can resolve (`'system'`) are never stored resolved: the cookie holds the choice, the resolved value is client-derived state that is `undefined` during SSR and hydration (`resolvedTheme`, `systemTheme`), and the DOM gets it from the inline script before paint.
5. **Script mode**: enum, boolean, number and string prefs declare `.reflect(target, valueMap?)`, where target is `'class'` (enums only), `data-*` or a `--css-var`, on `<html>`. `prefsScript(prefs)` (`cookie-prefs/script`) returns fixed hand-written code plus a JSON config with `<` escaped (no `Function.prototype.toString`, which broke next-themes in #370). React renders it as `<script>` with `type="text/javascript"` on the server and `type="text/plain"` on the client plus `suppressHydrationWarning`, the fix from the Next.js docs: React does not warn for data-block scripts. `nonce` is a prop. The script also runs in server mode, because `<html>` attributes cannot depend on `cookies()` under Cache Components.
6. **Client writes** go straight to `document.cookie` (synchronous, works on plain-HTTP localhost, `get()` after `set()` is consistent); local subscribers are notified synchronously; other tabs learn via the CookieStore `change` event where available, else a `BroadcastChannel` message posted after each write. No Server Action round trip. Server Components that read prefs via `getPrefs` are not refreshed: when server output depends on a pref, the app calls `router.refresh()` after `set` (documented pattern, not automatic, so a sidebar toggle never refetches the page).
7. **Not in v1**: see "Non-goals".

Other decisions:

- `PrefsProvider` in `cookie-prefs/next` defaults to `mode="script"`: dropping it into the root layout must not make the whole app dynamic or break Cache Components builds. `mode="server"` is opt-in for apps that are dynamic anyway.
- `pref.json` requires a Standard Schema: cookies are user-controlled input, so there is no unchecked `json<T>()`. Use `pref.custom()` as the escape hatch. Validation is synchronous; a schema returning a Promise reads as the default. The cookie holds `JSON.stringify(value)` and every read validates it, so writes (`set`, `toCookie`) take the schema input (without `undefined`; clear with `reset()`), while reads, the updater's `prev` and `.default()` (returned as is) use its output. They differ only for transforming schemas: `z.string().transform(...)` is written as a string.
- Invalid or missing cookie means default, never throw; this includes `parse` throwing, JSON errors, out-of-list enum values and `NaN`.
- **Renamed enum values**: `pref.enum([...]).migrate({ old: 'current' })` reads a cookie holding an old name as its current value on every read path (`get()`, `read()`, `readPrefs`, `getPrefs`, snapshot hydration, client reflection, the inline script, `reapply`), so renaming a value does not reset its users to the default. Enums only (the method is typed on `EnumPrefBuilder` alone). Reads stay pure: the cookie keeps the old name until the next `set()` writes the current one. One level, no chains and no versioning: each value must be a current value (types; at runtime anything else is dropped) and a key must not be one (types reject it via the map's own key type; at runtime a current value always reads as itself, so such a key is ignored). `EnumPrefBuilder.values` stays the list of current values; repeated calls add to the map, later keys winning.
- The theme preset stores in a cookie named `storageKey` (default `theme`), reads a next-themes value from `localStorage[storageKey]` once when the cookie is missing and moves it to the cookie (removing it from `localStorage`), passes nested providers through like next-themes, and is script-mode only (no `cookies()` read).
- **Theme on the server** (opt-in, issue #87): apps moving from next-themes that render `<html className>` or other content from the theme on the server need the stored name there (`@wrksz/themes` has `getTheme()`). Two server-only entries, so `cookie-prefs/theme` (a `'use client'` bundle) does not change and apps that do not import them are unaffected. `readTheme(source, options)` in `cookie-prefs/theme/server` is a pure function over the core's `CookieSource` (header string, cookie store, plain map), so React Router, Remix and any Request handler get it; it imports only the core. `getTheme(options)` in `cookie-prefs/theme/next` is the App Router convenience: it imports `next/headers` through `cookie-prefs/next`, so it has its own entry that non-Next code never loads, and `cookie-prefs/next` (7 B under its budget) does not grow. Names follow the core: `read*` takes a source, `get*` reads the current request, like `readPrefs` / `getPrefs`. Both return what `useTheme().theme` holds after hydration for the same cookie and the same provider options: `readTheme` builds the provider's pref (`pref.enum` over `themes`, `'system'` when `enableSystem` is on and the keys of `value`, `.default(defaultTheme)`, cookie `storageKey`) and reads it with the core, so decoding, quotes, duplicates, the 4096-character cap and the default fallback are the core's. `getTheme` takes the raw cookie the way `getPrefs` reads the request (the `Cookie` header parsed like the browser, plus same-request writes from `cookies()`) and passes it to `readTheme`. `'system'` is returned as is (the OS scheme is client-only) and `forcedTheme` is left to the caller. With a literal `themes` tuple the result is that union plus `'system'`, and `defaultTheme` and the `value` keys must be listed (`NoInfer`), so the type covers every name that can come back; otherwise `string`. Reading request cookies makes the route dynamic, which is why the provider itself stays script-only: the inline script remains the source of truth before hydration and `<html>` keeps `suppressHydrationWarning`. The client entry does not import the helper (it would grow); the provider's pref construction is copied, and a parity test runs the client, `readTheme`, `getTheme` and the inline script over a table of cookies and options.
- **theme-color** (opt-in, issue #90, next-themes #78): `<meta name="theme-color">` follows the theme shown, through `ThemeColor({ colors, nonce })` in `cookie-prefs/theme/color`, a client entry of its own: `cookie-prefs/theme` is 20 B under its budget, and apps that do not import the entry get no bytes and no behaviour. It is a component rendered inside `ThemeProvider` rather than a provider prop (next-themes 1.0 beta has `themeColor`), so the provider does not grow for everyone, and it is built on the public `useTheme()` alone (`theme`, `resolvedTheme`, `forcedTheme`, `systemTheme`): `cookie-prefs/theme` did not change. The colour is the one of the theme `paint` applies: `forcedTheme || resolvedTheme`, a forced `'system'` resolved with `systemTheme` when `enableSystem` is on; nothing is done while `theme` is `undefined` (SSR, hydration, no provider), so the tag the script added is never removed during hydration. `colors` is a plain map from theme name (not DOM value) to a colour string, like `value`; a single constant colour needs no library, and `var(--x)` is not resolved (that needs the theme applied first and a computed style read in both paths).
  - *Before hydration.* Weighed: (a) an inline script of its own repeating the theme script's resolution, (b) a smaller script reading what the theme script wrote on `<html>`, (c) static `<meta media>` pairs plus a script for explicit choices. (b) has to invert the DOM value, which needs the provider's `attribute` and `value` and is ambiguous (two names mapped to one DOM value, other classes on `<html>`, a forced name outside the list, an invalid class name the theme script could not add). (c) still needs a script for every explicit choice, and the static tags it renders are React's, which the script would have to rewrite before hydration. Chosen: (a), without asking for the provider's props again. The script walks `document.scripts` back to the closest one whose text starts with the theme script's fixed head `(function(k,l,a,m,d,f,s,c){`, reads the config back from its JSON string literal (as `cookie-prefs/react` reads `prefsScript`'s), and runs the theme script's resolution statements, copied byte for byte inside a function with the same parameter names (cookie, then a next-themes value in `localStorage`, validation, default, `forcedTheme`, `'system'`). A test checks that the copy is part of the theme script, and a parity test runs the theme script followed by this script, and the client, over the theme parity table (`src/theme/__tests__/rows.ts`, shared with the theme script's own parity test) with a full and a partial colour map, and checks that the colour belongs to the theme the theme script painted. It is rendered like the provider's script (`text/javascript` and nonce on the server, `text/plain` on the client, `suppressHydrationWarning`, the first `{ __html }` object kept), so React 19 does not warn and enforced Trusted Types behave as for the provider. No request API is read.
  - *Existing tags.* `ThemeColor` owns one tag, `<meta name="theme-color" property="cookie-prefs">` without `media`, and keeps it the first theme-color tag in tree order: inserted before the first existing one, or appended to `<head>` when there is none, by the script and by every client update. Browsers use the first tag whose `media` matches and whose `content` is a colour, so the owned tag wins. Tags the page renders (Next.js `viewport.themeColor`, with or without `media`) are never modified, moved or removed: React keeps owning them and Next may replace them on client navigations without a fight. For a theme without a colour the owned tag is removed and the page's tags apply. Rewriting the page's tags was rejected: React owns them and re-renders or replaces them on navigation (next-themes #78 reports `viewport.themeColor` overriding next-themes 1.0 beta), and React 19 finds the server element of a hoisted `<meta>` by its `content`, so a rewrite before hydration makes it insert a second tag. The marker is `property`, not a `data-*` attribute, because before inserting a hoisted `<meta>` React 19 adopts an existing unowned one with the same `content`, `name`, `property`, `http-equiv` and `charset`: with only a `data-*` marker React would adopt the owned tag for a page tag of the same colour, then rewrite or remove it when that tag changes. React 19 skips unowned `<meta>` elements when it hydrates `<head>`; React 18 leaves extra trailing nodes in `<head>` alone but hydrates the other children by position, so in a React 18 app that renders `<head>` with a theme-color tag of its own, React claims the owned tag for that `<meta>` and warns in development that `content` did not match (no error, no client re-render; the colour shown stays right, but React may later rewrite or remove the tag). Documented; every Next.js App Router version runs React 19. `src/theme/color/__tests__/document.test.tsx` hydrates a whole React-rendered document both ways, and the `React 18 compatibility` CI job runs it on React 18.

## Implementation notes

- **Entry boundaries.** `cookie-prefs/react`, `cookie-prefs/theme` and `cookie-prefs/theme/color` are client modules: their built files start with `'use client'`, prepended to the ESM and CJS output in tsup `onSuccess` (tree shaking strips a `banner` directive, and one config avoids `clean` races between parallel builds). `cookie-prefs/next`, `cookie-prefs/theme/server` and `cookie-prefs/theme/next` are server-only (no `'use client'`); `cookie-prefs/next` imports `next/headers.js` (with the extension: `next` has no `exports` map, so Node ESM, e.g. vitest in an app where cookie-prefs is not bundled, cannot resolve `next/headers`; the file exists in Next 14 to 16), and `cookie-prefs/theme/next` reaches it only through `cookie-prefs/next`, so `cookie-prefs/theme/server` stays loadable without Next. Server helpers must never live in a client entry, because a Server Component calling them gets a client reference.
- **No duplicated state.** Runtime imports between entries use package specifiers (`'cookie-prefs'`, `'cookie-prefs/react'`, `'cookie-prefs/script'`, `'cookie-prefs/next'`, `'cookie-prefs/theme'`, `'cookie-prefs/theme/server'`) marked external in tsup, not relative paths, so the cross-tab listener and stores exist once and the client boundary survives bundling. Type-only imports from `../core/types` are fine.
- **Duplicate copies.** Handles are portable across copies of the core (ESM + CJS, two versions): what `prefsScript` (`cookie-prefs/script`) needs lives on the handle under a `Symbol.for` key, not in module state, and the script entry repeats the key instead of importing the core; two copies of `cookie-prefs/react` still mean two React contexts, which is inherent to React.
- **Next `PrefsProvider`** is an async Server Component: in `'server'` mode it passes the request snapshot that `getPrefs` reads too; in both modes it passes `prefsScript(prefs)` (from `'cookie-prefs/script'`) and `nonce` to the client `PrefsProvider` from `'cookie-prefs/react'`. `prefs` itself never crosses to the client.
- **Next request snapshot.** `snapshotPrefs(prefs, header)` over the raw `Cookie` header from `headers()`, so the server parses like the browser and the inline script. Per pref, a `cookies()` value that equals none of the header's values for that name, decoded as Next decodes them (URI-decoded, quotes kept, a bare name is `'true'`, malformed values skipped), was written earlier in this request and replaces it; `''` (left by `delete()`) removes it, so a same-request `set('')` of a string pref also reads as missing until the next request. A write equal to a later duplicate in the header is not detected.
- **Snapshots must be stable** for `useSyncExternalStore`: cache the parsed value per pref by raw string, so `json` and `custom` prefs do not return a new object on every read. Only where a DOM exists: on the server every read parses again, because a cached object would be handed to every later request, and one that mutates it would leak into the next (`typeof document` decides; the hydration read of a snapshot runs in the browser, so it stays cached and stable). Returned values, and the `.default()` value on both sides, are shared: the documented contract is to treat them as read-only.
- **Own-write echo.** The CookieStore `change` event also fires for this tab's writes; compare raw values before notifying.
- **Listeners.** They run synchronously in subscription order, only when the value changed. A listener that throws is caught and its error thrown again from `setTimeout`, so `set()`/`reset()` never throw because of a listener, every other listener and every other pref in a cross-tab re-check still runs, and the error still reaches `window.onerror`. A listener that writes the pref runs a nested check that notifies everyone of the newer value; the outer loop then skips the listeners it had not reached, which would otherwise get the older value last. Listeners are a `Set`, so the same function subscribed twice is one listener, removed by the first unsubscribe.
- **Tab shown again.** The hub also listens for `visibilitychange` while anything subscribes and re-checks every subscribed pref when the tab becomes visible, so hooks follow a change nothing announced (a server `Set-Cookie` without CookieStore, a tab on a sibling subdomain, which a per-origin `BroadcastChannel` does not reach) at the same moment the provider re-applies `<html>`. It lives in the core rather than the provider: the provider only holds the script string and cannot reach the store's re-checks without a new core export, and it also helps apps without a provider.
- **No channel.** Where `new BroadcastChannel()` throws (an opaque origin, e.g. a sandboxed iframe without `allow-same-origin`, which also lacks CookieStore) or does not exist, the hub works without one: subscribing never throws, local writes notify as usual, other tabs are not reached.
- **Encoding.** Names and values are `encodeURIComponent`-encoded; booleans are `'true'`/`'false'`; enums and numbers are stored as is; `json` is `JSON.stringify` then encoded.
- **Whitespace.** Browsers strip only spaces and tabs around cookie names and values and keep other whitespace (U+00A0, U+2028, U+FEFF...), which a server or a sibling subdomain can send in raw UTF-8. `document.cookie` therefore never has spaces or tabs at the edges, and the inline script and `reapply` split it on `'; ' + name + '='` without trimming. The header reader (`rawOf`, used by `get()`, `read()`, `readPrefs`, `snapshotPrefs` and `cookie-prefs/next`) also tolerates spaces and tabs around names, values and `;` in hand-written headers, but trims nothing else (`String.prototype.trim` would), so all read paths agree. Its pattern is anchored and every group may be empty, so it never backtracks: linear in the header length.
- **`__proto__`.** Objects keyed by pref keys or cookie names (`definePrefs`, `readPrefs`, `snapshotPrefs`, the Next request snapshot) are built with `Object.fromEntries` or spreads, never by assignment, so a pref keyed `__proto__` or a cookie named `__proto__` is an own data property instead of a prototype change. Only own keys of the shape are read, so a polluted `Object.prototype` adds no prefs.
- **Encoding at the edges.** `Pref.name` is the encoded cookie name (the key in `document.cookie`, the `Cookie` header and `PrefsSnapshot`). Snapshots and cookie stores/maps passed as `CookieSource` hold URI-decoded values; only a header string is decoded by cookie-prefs. `toCookie().value` is not URI-encoded: frameworks encode on set, code writing a raw `Set-Cookie` header must call `encodeURIComponent`.
- **Nonce.** Browsers hide `nonce` after load, so render it on the server only or keep `suppressHydrationWarning` on the script. The React `PrefsProvider` renders `type` and `nonce` from `typeof document` at render time (server: `text/javascript` + nonce; client: `text/plain`, no nonce) with `suppressHydrationWarning`; hydration never patches attributes, so the server element keeps its nonce.
- **Re-applying reflection.** The client provider runs the `script` string again in a layout effect on mount (dev Strict Mode / remounts can reset `<html>`) and on `visibilitychange` to visible, so prefs nobody in this tab subscribes to follow other tabs when the tab is shown again (subscribed prefs follow at once through the store, and the store re-checks them on `visibilitychange` too). Nothing is executed: `cookie-prefs/react` reads the JSON config back from the `script` string (the fixed source ends in `})(` and holds `})("` nowhere else, and the string literal after it escapes every `"`, so the first `})("` marks the start of the literal, which runs to the final `)`) and applies it from `document.cookie` with `classList`, `setAttribute` and `style`. That code is a step-by-step port of the inline script (cookie lookup, decoding, validation, default, class swap, removal, per-pref `try`); a parity test runs both over a table of configs and cookies, so keep them in sync. With no script element, `eval` or script text assignment, CSP and enforced Trusted Types (`require-trusted-types-for 'script'`) have nothing to check, and the client needs no nonce; it stays on the server-rendered script. No core export was needed. The provider renders only its first `script` string for its whole lifetime: new text on a hydrated `<script>` would be an `innerHTML` write that enforced Trusted Types reject, and the element already ran or is inert. A later `script` is still re-applied. It also keeps the `{ __html }` object of that first render in state and passes the same object on every render: React 19.0 to 19.2 (and the React canaries that Next 14 and 15 bundle for the App Router) compare `dangerouslySetInnerHTML` by object identity and assign `innerHTML` again on any re-render with a new object, even when the text is the same; React 18.3 and 19.3+ compare the `__html` string. A provider re-rendered after hydration (a new `snapshot` from a refreshed Server Component payload, a parent re-render) would otherwise hit enforced Trusted Types on those versions.
- **Script config as a string.** The inline scripts of the core and of the theme preset get their config as JSON inside a JSON string literal and `JSON.parse` it. As an object literal, an enum value (or a theme or `value` key) named `__proto__` would set the map's prototype instead of a key, so the script would read it as invalid while the client (`Object.fromEntries`) accepts it. The literal is ES5 once U+2028/U+2029 are escaped; `<`, `>` and `&` stay escaped for HTML.
- **Reflection on every check.** The store applies `<html>` reflection on every `set`/`reset` and every re-check, before the `Object.is` guard that only gates listeners. The last value a handle saw goes stale while nothing subscribes (the provider's re-apply, another tab, a server `Set-Cookie`), so guarding the DOM write with it lost updates, e.g. a hook-less `set(o => !o)` after another tab toggled back.
- **Client and script apply alike.** `apply()` mirrors the script's single `try` per pref: an invalid attribute name or class stops that pref's remaining targets, and the class swap iterates the value map with `for…in` like the script. In development (`process.env.NODE_ENV != 'production'`, which bundlers replace and drop from production builds, so it costs nothing in the size budget) `definePrefs()` throws when a `'class'` target maps a value to an empty class or one with ASCII whitespace, which `classList` would reject for every value. The enum value map is read by own keys on both sides. TypeScript rejects a partial map for an enum with a value named like an `Object.prototype` member (`toString`), because the map's type then requires that key to be a string; listing the key in the map compiles.
- **Enum migration needs no script change.** `bind` builds one `Map` from raw value to value for an enum: the `.migrate()` entries whose value is a current value, then each current value to itself, so a current value always wins over a key of the same name. The parser is a lookup in that map (a `Map`, so `toString`, `__proto__` or a polluted `Object.prototype` is never a valid raw value), and the reflection value map (`Kind`) gets one key per map entry, an old name mapping to the DOM string of its current value. The inline script and `reapply` already validate a raw value by own key of that map and apply what it maps to, and the class swap removes every value of the map, where duplicates are harmless, so neither changed (`cookie-prefs/script` and `cookie-prefs/react` kept their size; the reflection layout and its `Symbol.for` key are unchanged). The dev-time class check also sees only DOM strings of current values. A snapshot keeps the raw old name; the server render and hydration both parse it with the same map, so they agree. `usePref`'s Safari refresh compares the stored text with the current value's text, so it never re-writes a cookie holding an old name: in Safari such a script-written cookie still expires 7 days after its last write unless something calls `set()`.
- **Reflected strings are cookie-controlled.** A reflected `pref.string()` (or a number) writes whatever the cookie holds into a `data-*` attribute or CSS variable. Cookies can be set by sibling subdomains (cookie tossing) or by the user, so only reflect free-form strings whose value you would accept from an attacker in that attribute or variable (no `url()` in the variable, no selectors that leak it); prefer an enum.
- **Unreadable cookies.** In a sandboxed iframe without `allow-same-origin` (opaque origin) reading or writing `document.cookie` throws. `get()` then returns the default, and `set()`/`reset()` write nothing, notify nothing and never throw. The inline script throws there too and leaves `<html>` alone.
- **Lone surrogates.** `encodeURIComponent` throws on lone UTF-16 surrogates (e.g. `'😀abc'.slice(1)`). `set()` stores them as U+FFFD via `String.prototype.toWellFormed` where it exists (browsers since 2023, Node 20); without it nothing is written and `set()` does not throw. `json` prefs are unaffected, since `JSON.stringify` escapes lone surrogates. `toCookie()` returns the value as is, so a framework that encodes it may still throw.
- **Safari's 7-day cap.** Safari (ITP) caps cookies written through `document.cookie` at 7 days, whatever `Max-Age` says (https://webkit.org/blog/8613/intelligent-tracking-prevention-2-1/). Reads never refresh a cookie, so without help a pref would revert 7 days after its last write, even for a daily visitor. `usePref` therefore re-writes the pref's cookie once per handle per page load, in an effect (never during render, never on the server), so the window slides with visits. Only a cookie meant to live longer than 7 days is refreshed (`pref.toCookie(value).maxAge > 604800`): re-writing a shorter one with its own `Max-Age` would keep it alive for a regular visitor in every browser, so a "snooze for a day" pref would never expire. It writes only when the value is defined and the cookie holds exactly the text the write would produce: the stored text (found with the string search `'; ' + name + '='` in `document.cookie`, up to the next `;`, since the core has no "raw value" call) must equal `encodeURIComponent(pref.toCookie(value).value)`, byte for byte. A cookie that is absent, invalid or unknown to this build (a value written by a sibling subdomain sharing the cookie through `domain` but accepting other values, by a newer release before a rollback, an enum value this build lacks) reads as the default, so writing it back would replace the user's choice with the default in every browser: it is left alone until an explicit `set()`. The comparison is on the stored text, never on decoded or parsed values, so it cannot call a different value "the same": equal text means the write changes only the cookie's attributes and expiry. It can call the same value "different" (quoted, encoded otherwise than by `encodeURIComponent`, such as `%64ark`, or `%21` from a writer that also encodes `!`, or json with other spacing or key order); such a cookie is simply not refreshed, the safe direction. The same text parses to the same cached value (same object for json and custom prefs), so the core sees no change and notifies nobody: no re-render, no hydration mismatch. The rule assumes a deterministic `serialize`, as every built-in codec is. A module-level `WeakSet` of handles makes Strict Mode's second effect run and other components using the same pref a no-op. The write uses the handle's attributes, which must match those of any server write (`toCookie()` uses the same). Prefs no hook uses are refreshed only by `set()`. A cookie set by the server (`Set-Cookie`, e.g. middleware writing `pref.toCookie(value)`) is not capped, but the refresh re-writes the cookie of any pref a hook reads from the page, so a server write keeps its long lifetime in Safari only for prefs no hook uses.
- **Known limitations (core).** `set(-0)` reads back `0` (`String(-0)` is `'0'`). The same listener function subscribed twice is one listener (see above). A `.default()` value is returned as is to every reader, on the server too. jsdom strips all whitespace around cookies, unlike browsers, so the parity tables that cover it fake `document.cookie`. An empty cookie name (`.options({ name: '' })`, or an empty key without prefix) is written as a bare value that no read path takes; `definePrefs()` throws for it in development only.
- **Nested providers** merge their snapshots (inner keys win); a provider without a snapshot keeps the outer one.
- **Script mode trade-off.** Hooks render defaults until hydration ends; anything visible before hydration must come from reflected attributes plus CSS. Document this next to `mode`.
- **`get()` on the server** returns the default; add a dev-only warning pointing to `read()` / `getPrefs()`.
- **Size budget.** All of core (parsers, cookie codec, store, sync, Standard Schema glue, client reflection) must fit 2 KB gzip. `prefsScript` and the inline script source live in `cookie-prefs/script` with their own budget, so the core does not carry them; discuss moving more out of the core before touching the limit. The theme server helpers have their own entries and budgets (`cookie-prefs/theme/server` 255 B, `cookie-prefs/theme/next` 200 B, other entries excluded), so neither `cookie-prefs/theme` (client) nor `cookie-prefs/next` grows; so does `cookie-prefs/theme/color` (1030 B, `cookie-prefs/theme` and React excluded), which leaves `cookie-prefs/theme` (1880 of 1900 B) as it is.
- **Tooling.** `tsconfig.json` uses `"jsx": "react-jsx"`; its `paths` and the vitest `resolve.alias` map `cookie-prefs`, `cookie-prefs/react`, `cookie-prefs/script`, `cookie-prefs/next`, `cookie-prefs/theme` and `cookie-prefs/theme/server` to `src/`, so typecheck and tests run from source while tsup keeps them external.
- **Sizes.** `size-limit` checks `cookie-prefs/react`, `cookie-prefs/script`, `cookie-prefs/next`, `cookie-prefs/theme`, `cookie-prefs/theme/server`, `cookie-prefs/theme/next` and `cookie-prefs/theme/color` too, with peers and the other entries excluded (`ignore: ['cookie-prefs']` covers its subpaths).

### Theme preset (`cookie-prefs/theme`)

- **Storage.** One `pref.enum(...).default(defaultTheme).options({ ...cookie, name: storageKey })` per provider, built with the core and keyed on the provider's config and on `cookie` as JSON (inline `themes` / `value` / `cookie` literals do not recreate it or re-run its effects). `cookie` is the one prop next-themes does not have: the core's `CookieOptions` (`domain`, `sameSite`, `secure`, `partitioned`, `path`, `maxAge`), so the theme can be shared across subdomains (`domain`) or written inside a cross-site iframe (`sameSite: 'none'`, `secure`, `partitioned`), where the default `SameSite=Lax` write is rejected. Valid stored names are `themes`, the keys of `value` (the next-themes README stores `pink` with only `value={{ pink: ... }}`) and `'system'` when `enableSystem` is on. Core `.reflect('class')` is not used, since it would write `system` as a class. `setTheme` ignores names outside that list instead of writing a cookie that reads back as the default.
- **Inline script** (`src/theme/script.ts`). Fixed ES5 source called with `.apply(0, JSON.parse(config))`, where the config is JSON inside a JSON string literal with `<`, `>`, `&`, U+2028 and U+2029 escaped (a local copy of the core helper, which is internal; as an object literal, a theme or `value` key named `__proto__` would set the prototype instead of a key, see "Script config as a string"): cookie name, `localStorage` key, attributes, a map from every valid stored name to its DOM value, default, forced theme, `enableSystem` and the fallback `color-scheme`. It reads the cookie (URI-decoded, quotes stripped, validated, default on a miss or a decoding error), or `localStorage[storageKey]` when the cookie is absent, then applies `forcedTheme` first, resolves `system` with `matchMedia`, maps through `value`, swaps the class / sets the attributes and sets `color-scheme`. The source never comes from `Function.prototype.toString`, so `keepNames` / SWC `__name` helpers cannot break it (next-themes #370). It is rendered like `PrefsProvider`'s script: `text/javascript` plus nonce on the server, `text/plain` on the client, `suppressHydrationWarning` (next-themes #385, #387). `scriptProps` are spread first, so they cannot change `type`, `nonce` or the content. The provider renders only its first script string for its whole lifetime: later prop changes (a `forcedTheme` per route) would otherwise make React write new text into the hydrated `<script>`, which enforced Trusted Types reject and which is useless anyway, since the element already ran or is inert. The live config drives the client. It keeps the `{ __html }` object too, for the same reason as `PrefsProvider`: this provider always re-renders right after hydration (the `useSyncExternalStore` server snapshots are `undefined`, the client ones are not), and React 19.0 to 19.2, including the canaries bundled by Next 14 and 15, re-assign `innerHTML` for a new `dangerouslySetInnerHTML` object with unchanged text. That write broke hydration under enforced Trusted Types on Next 14 and 15 (#45); with one object for the provider's lifetime, React never touches the hydrated script's text on any version.
- **Client.** `theme` comes from `useSyncExternalStore` over the pref and `systemTheme` from one over `matchMedia` `change` events (through `addListener` in Safari and iOS before 14, which lack `MediaQueryList.addEventListener`, as next-themes does); both use `undefined` as the server snapshot, so `theme`, `resolvedTheme` and `systemTheme` are `undefined` during SSR and hydration and resolve right after. One layout effect runs on mount and on every change: it migrates `localStorage` once or, the first time a provider sees an existing theme cookie in this page load, re-writes it with the same value against Safari's 7-day cap when its `maxAge` is longer than 7 days and the cookie holds exactly the text the write would produce, `encodeURIComponent(theme)` (see the implementation note; a theme this provider does not list, for example one listed by another subdomain sharing the cookie through `cookie={{ domain }}`, reads as the default and is left alone until `setTheme()`; a module-level set of cookie names keeps it to once across Strict Mode, remounts and prop changes, and an enum value always reads back the same, so nothing re-renders), then calls `paint`, a step-by-step DOM port of the script (no script element, no `eval`, so CSP and Trusted Types have nothing to check), and listens for `visibilitychange` to repaint and re-read the cookie. `paint` always reads the current cookie, never rendered state, so an effect that re-runs when `<Activity>` reveals a cached tree cannot bring back an old theme (next-themes #375). A parity test runs the script and the client over a table of configs and cookie / storage states; keep both in sync.
- **Migration.** When the cookie is absent and `localStorage[storageKey]` holds a valid name, the client writes it to the cookie (the script already painted it) and, once the cookie reads back, removes the `localStorage` key; an invalid value is removed too. So the move runs once: when the cookie later goes away (expiry, Safari's cap on script-written cookies, cookies cleared) the theme falls back to the default, in the script and on the client alike, instead of an old next-themes value coming back over a newer choice. The trade-off: rolling back to next-themes no longer keeps the user's choice; it starts from its default. When the cookie write does not stick (cookies blocked) the value stays, so nothing is lost. Storage that throws on access, read or removal is ignored.
- **`disableTransitionOnChange`.** As in next-themes: a `<style>` that sets `transition: none` on everything is appended, the theme is applied, a computed style is read to force a restyle, and the style is removed on the next tick. The style carries `nonce`, so a strict `style-src 'nonce-…'` policy allows it. Without a nonce, such a policy blocks the style: transitions are not disabled, the theme still switches.
- **Differences from next-themes 0.4.6.** The choice is a cookie, not `localStorage`. Invalid stored values and invalid `setTheme` names fall back to or keep a valid theme, where next-themes applies any string. `value` is applied the same way by the script and the client (next-themes' script ignores it for `data-*` attributes, and the client removes the attribute for unmapped names). A forced `'system'` is resolved by the script too. `color-scheme` is set the same way before and after hydration. Class removal covers every valid theme's DOM value. Only `class` and `data-*` targets exist (types). `theme` is `undefined` during hydration, where next-themes already returns the `localStorage` value and so mismatches without a mounted guard. Other tabs are followed through the core (CookieStore or BroadcastChannel) instead of the `storage` event. The transition style drops the obsolete vendor prefixes.
- **Known limitations.** A `ThemeProvider` first mounted on the client (not hydrated, for example in a nested layout first reached by a client-side navigation, in a component loaded with `ssr: false`, or remounted under a new `key`) sets the inert script's text through React, which enforced Trusted Types reject, as for `PrefsProvider`. A hydrated provider never writes script text, whatever its props or re-renders, on React 18 and 19 (tested on Next 14, 15 and 16). With cookies blocked, the script shows the `localStorage` value but the client falls back to the default. A forced theme outside the valid list keeps its class after `forcedTheme` is removed. The preset is script-mode only: `useTheme()` is `undefined` until hydration. The opt-in `readTheme` / `getTheme` read the stored theme on the server but cannot see a next-themes value still in `localStorage`, so the first request after a move from next-themes gets the default until the client has moved it to the cookie; and `cookies()`-style stores passed to `readTheme` follow their own parsing (Next's lets the last duplicate win and keeps quotes), so pass the header string where the browser's reading must match.
- **Known limitations (`ThemeColor`).** Render one at a time: two would share the owned tag, and unmounting either removes it. It must be inside `ThemeProvider` and after its script (it always is when rendered among the provider's children); with no theme script before it, the inline script does nothing and the client takes over after hydration. The owned tag is put back in front only when the colour changes, so a theme-color tag inserted before it in the meantime wins until then (React appends its tags, so Next's do not). The page tag lookup is `meta[name="theme-color"]`, case-sensitive, where browsers match the name in any case. First mounted on the client (not hydrated), it sets its inert script's text through React, which enforced Trusted Types reject, like the provider. React 18 with a React-rendered `<head>` holding a theme-color tag: a development warning and a tag React may later rewrite (see Other decisions). The jsdom unit tests render on the server with modules loaded next to a DOM, where React 18's server renderer warns about the layout effects the client uses; real server rendering (no DOM at module load) is checked without warnings in `server.test.tsx`. `var(--x)` colours are not resolved.

## Non-goals for v1

- SSR of the theme preset itself (a server mode for `ThemeProvider` / `useTheme`). The stored theme is readable on the server with the opt-in `readTheme` / `getTheme` (see Other decisions).
- Per-page forced theme without a provider (#226). (`theme-color`, next-themes #78, is the opt-in `cookie-prefs/theme/color`, see Other decisions.)
- Automatic `router.refresh()` after writes, Server Action writes, optimistic server sync.
- Pages Router integration (use `cookie-prefs/react` with `snapshotPrefs` in `getServerSideProps`).
- Async Standard Schema validation, versioning of stored values, encryption or signing. (Renamed enum values are covered by `.migrate()`, see Other decisions.)
- Combined cookies, `localStorage` or `sessionStorage` backends, URL state (use nuqs).
- Reflection targets other than `<html>`, and system-preference resolution for generic prefs (the theme preset owns it).
- A batch hook (`usePrefs`), selectors, devtools, middleware helpers.
